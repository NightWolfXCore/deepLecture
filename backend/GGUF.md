# Импорт локального GGUF в Ollama

Для текущего проекта нужен основной файл весов **Qwen3.5 4B** в поддерживаемом
Ollama GGUF-формате. Файл `mmproj*.gguf` сам по себе не содержит языковую модель.
Пример ниже рассчитан на один целый GGUF, не на отдельную часть split-модели.
Ollama на хост отдельно не устанавливается: используется наш Docker-сервис.

**Windows / PowerShell:** используйте [отдельную инструкцию](GGUF-WINDOWS.md).
Она содержит нативные команды Windows; Bash/Git Bash не требуется.

## Как определить квантизацию

Расширение GGUF обозначает контейнер, а не тип квантизации. Имя и размер файла
могут дать подсказку, но не доказывают Q4_K_M. Не переименовывайте неизвестный
файл в Q4_K_M в качестве «преобразования» — это не меняет его содержимое.

После импорта выполните `dgg exec ollama ollama show deeplecture-qwen3.5:4b`:
в разделе Model будут архитектура, число параметров и **quantization**.
Возможны Q4_K_M, Q8_0, F16 и другие варианты. F16/BF16 требуют больше памяти,
чем 4-битные варианты. Поддерживаемые GGUF не ограничиваются Q4_K_M.
Для точного состава отдельных тензоров смотрят метаданные/типы тензоров GGUF;
название общей квантизации не означает одинаковую точность каждого тензора.

Если нужно узнать тип **до импорта**, можно прочитать GGUF утилитой
`gguf-dump` из пакета `gguf` проекта llama.cpp: интересуют `general.file_type`
и типы тензоров. Номер file_type интерпретируется по enum соответствующей
версии llama.cpp. Для простого подключения дополнительная Python-утилита
не нужна — достаточно `ollama show` после импорта.

## 1. Разместить исходный файл

Команды ниже — для Bash/Git Bash, из корня deepLecture:

```sh
mkdir -p storage/llm
# Скопируйте ваш целый GGUF в storage/llm/model.gguf.
# Имя model.gguf не делает предположений о его квантизации.
```

Если файл исходно называется иначе, при копировании можно дать ему это имя:
это меняет только путь. Части split-GGUF нельзя превращать в целую модель
переименованием одной части. Для split-варианта нужны все части с исходными
именами и соответствующий wildcard в FROM; приложенный Modelfile использует
один файл. Если сомневаетесь, начните с single-file GGUF.

`storage/` исключена из Git и Docker build-контекста. Для модели в другом
месте задайте абсолютный `GGUF_DIR` — Compose смонтирует его в `/imports`.
Папка и файл должны быть доступны на чтение Docker. При импорте дополнительно
понадобится место под модель в томе `ollama-models` — планируйте место и для
исходного GGUF, и для импортированной копии.

## 2. Подготовить конфигурацию

Если файлов ещё нет, создайте их без перезаписи существующих:

```sh
cp -n .env.example .env
cp -n infra/llm/ollama.env.example .env.llm
```

Задайте свой DB_PASSWORD в `.env`. В существующем `.env.llm` измените только
нужные LLM-поля (не коммитьте файл):

```dotenv
LLM_BASE_URL=http://ollama:11434/v1
LLM_MODEL=deeplecture-qwen3.5:4b
LLM_API_KEY=
LLM_AUTH_MODE=none
LLM_REASONING_EFFORT=none
LLM_ALLOW_HTTP=true
LLM_TIMEOUT=300
OLLAMA_IMAGE=ollama/ollama:0.40.12
OLLAMA_CONTEXT_LENGTH=16384
```

Имя `deeplecture-qwen3.5:4b` — локальный тег для импортированного файла.
Оно само по себе не подтверждает, что внутри именно 4B: это проверяется через
метаданные/`ollama show`. Отдельное имя сохраняет официальный `qwen3.5:4b`,
если он уже скачан через `ollama pull`.

## 3. Запустить Ollama и импортировать

В репозитории уже подготовлены:

- `infra/compose.gguf.yml` — монтирует GGUF-каталог и Modelfile read-only;
- `infra/llm/Modelfile.gguf` — `FROM /imports/model.gguf` и контекст 16384.

Определите команду с тремя Compose-файлами:

```sh
dgg() {
  docker compose --env-file .env --env-file .env.llm \
    -f infra/compose.yml -f infra/compose.ollama.yml \
    -f infra/compose.gguf.yml "$@"
}
dgg up -d ollama
dgg exec ollama ollama --version
dgg exec ollama ollama create deeplecture-qwen3.5:4b -f /config/Modelfile
dgg exec ollama ollama show deeplecture-qwen3.5:4b
```

Первый запуск требует доступного образа Docker; сам `create` использует
локальный GGUF и не требует `ollama pull` весов. Не запускайте `ollama pull`
для локального имени `deeplecture-qwen3.5:4b`.
Импорт **сохраняет исходную квантизацию**. Он не превращает F16 в Q4_K_M.
Если нужен Q4_K_M, скачайте соответствующий файл или отдельно подготовьте
квантизацию поддерживаемым GGUF-инструментом. Переименование не помогает.

## 4. Подключить worker и проверить конспект

После успешных create/show выполните реальный вызов нашего адаптера:

```sh
dgg build worker
dgg run --rm --no-deps worker python -m app.check_llm
```

Это не требует БД: проверяется вызов модели, JSON и существующие ID глав.
Если проверка успешна, на уже подготовленном стеке перезапустите worker:

```sh
dgg up -d worker
```

Worker читает env при старте. Простое редактирование `.env.llm` без пересоздания
контейнера не меняет модель у работающего процесса. Первый inference может
занять время на загрузку; качество русского конспекта и скорость затем
проверьте на реальной лекции. Ошибки импорта/JSON нужно устранить до демонстрации.

После импорта модель хранится в `ollama-models`, не только в исходном каталоге.
`down` сохраняет тома, `down -v` их удаляет. Для офлайн-проверки готового стека
добавьте `infra/compose.offline.yml` последним, как описано в [LLM.md](LLM.md).

В нашей среде файла пользователя пока нет: реальный импорт, квантизация и
inference этого GGUF не проверены. Конфигурация сама по себе не доказывает
совместимость конкретного скачанного файла.

Основание процедуры: [импорт GGUF в Ollama 0.40.12](https://github.com/ollama/ollama/blob/v0.40.12/docs/import.mdx).
